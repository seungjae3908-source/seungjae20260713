## §1. 프로젝트 개요

### 1.1 최종 목표

글로벌 암호화폐 선물 시장의 다수 종목을 대상으로 Long과 Short를 독립적으로 분석하고, 전략을 탐색·검증하는 멀티심볼 AI 연구 시스템이다.

- 1차 거래소: Bitget USDT-FUTURES
- 확장 대상: Binance, OKX, Bybit, Gate.io, KuCoin
- 감시 대상: 거래소가 제공하는 USDT 선물 계약 전체
- 분석 방향: Long / Short 독립 분석
- 전략 범위: Adaptive Grid, Trend, Breakout, Mean Reversion, Momentum, Volatility Breakout, Regime Switching
- 검증 흐름: 데이터 수집 → 신호 분석 → 백테스트 → Failure Memory → Paper Forward
- 실거래 전환: 별도 승인과 검증을 거친 이후에만 검토

### 1.2 현재 운영 범위

현재 작업은 연구·분석·시뮬레이션에 한정한다.

- 공개 시장 데이터 사용
- 실거래 주문 실행 금지
- 비공개 거래소 주문 API 사용 금지
- 사용자 별도 승인 없는 운영 배포 및 서비스 재시작 금지
- 실제 자금 운용을 검증 완료로 간주하지 않음

### 1.3 핵심 원칙

1. Fail-Closed: 필수 데이터가 불완전하면 정상 완료로 처리하지 않는다.
2. No-Look-Ahead: 미래 데이터를 지표·신호·백테스트에 사용하지 않는다.
3. Additive-Only: 기존 기준선 파일은 명시적 승인 없이 수정하지 않는다.
4. Independent Long/Short: 양방향 신호와 점수를 독립적으로 계산한다.
5. Read-Only First: 조사 후 승인된 최소 범위만 변경한다.
6. Evidence-Based: 실제 테스트와 데이터로 확인되지 않은 성능을 주장하지 않는다.

## §2. 최종 목표 아키텍처

### 2.1 데이터에서 검증까지의 흐름

1. 거래소 계약 목록 수집
2. Raw Universe 구성
3. Tradable Universe 분류
4. Strategy Candidates 선정
5. 종목별 시장 데이터 수집
6. 지표 및 시장 국면 계산
7. Long / Short 독립 신호 탐색
8. 후보 점수 및 순위 계산
9. 전략별 백테스트
10. Failure Memory 기록 및 재검증
11. Paper Forward
12. 검증 통과 전략을 향후 실거래 검토 대상으로 분류

위 항목은 최종 목표 아키텍처다. 현재 모든 단계가 하나의 통합 엔진으로 완성되었다는 의미는 아니다.

### 2.2 시장 데이터 계층

- 거래소 계약 목록과 티커 데이터를 분리 수집한다.
- Raw, Tradable, Strategy Candidates를 구분한다.
- 종목별 데이터 품질과 누락 여부를 기록한다.
- 캔들 데이터는 시간순으로 정렬하고 중복·비정상 데이터를 검증한다.
- 불완전한 캔들은 신호 계산에서 제외한다.

### 2.3 양방향 분석 계층

Long과 Short를 하나의 점수로 합치지 않는다.

- Long 신호와 Short 신호를 독립 계산한다.
- 각 방향별 전략 유형과 신뢰도, 무효화 조건을 기록한다.
- 시장 국면에 따라 전략 적합성을 별도 평가한다.
- 후보 순위는 방향별로 독립 산출한다.

### 2.4 검증 계층

백테스트 성과만으로 전략을 승인하지 않는다.

- 수수료와 슬리피지를 반영한다.
- 손절·익절 및 포지션 크기를 검증한다.
- 손실 구간과 실패 조건을 기록한다.
- IS/OOS 분리 검증과 Paper Forward를 거친다.
- 실거래 전환은 별도 승인 사항이다.

### 4.3 청산 판정 규칙

OHLC 봉만으로 TP와 SL 중 어느 가격이 먼저 도달했는지 알 수 없으므로, 같은 봉에서 둘 다 도달하면 보수적으로 SL을 우선한다.

Long:
- 저가가 SL 이하이면 SL 발생
- 시가가 SL 아래로 갭 하락했다면 시가를 손절 기준 가격으로 사용
- 그 외에는 SL 가격 사용
- TP는 TP 가격 사용

Short:
- 고가가 SL 이상이면 SL 발생
- 시가가 SL 위로 갭 상승했다면 시가를 손절 기준 가격으로 사용
- 그 외에는 SL 가격 사용
- TP는 TP 가격 사용
- 유리한 갭 체결은 가정하지 않는다.

위 가격은 청산 판정의 triggerPrice이며, 실제 체결 가격은 이후 슬리피지·수수료 계산과 구분해야 한다.

### 4.4 위험 기반 수량 및 증거금

`calculateRiskSizedQuantity`는 다음을 반영한다.

- 계좌 자산
- 진입 가격
- 손절 가격
- 허용 위험 비율
- 레버리지
- 이미 사용 중인 증거금
- 최대 증거금 사용 비율
- 진입·청산 수수료
- 진입·청산 슬리피지
- Long / Short 방향

위험 한도 기준 수량과 증거금 한도 기준 수량 중 작은 값을 선택한다.

이는 수량 산출 프리미티브이며, 거래소별 계약 승수·수량 단위·최소 주문 단위 등을 모두 반영한 완성 주문 검증기가 아니다.

### 4.5 청산 위험 계산의 한계

`calculateLiquidationRisk`는 현재 `NOT_COMPUTED`를 반환한다.

이유:
- 거래소별 유지증거금 구간 미구현
- Mark Price와 Last Price 차이 미반영
- 펀딩·보험기금·ADL 미반영

따라서 실제 청산가격이나 청산거리 계산이 완료되었다고 주장하면 안 된다.

Short는 각 유형의 하락 방향 대응 조건으로 별도 판단한다.

신호 데이터 설계 항목:
- symbol
- timeframe
- side
- signalType
- detectedAt
- entryReferencePrice
- marketRegime
- indicatorValues
- confidenceScore
- evidence
- invalidationConditions
- dataQuality
- strategyVersion
- isActionable

기본 `isActionable`은 false로 설계한다. 관측 신호와 실제 매매 후보를 구분한다.

### 7.5 후보 순위 설계

Long과 Short 점수를 독립 계산한다.

초기 제안 가중치:
- quoteVolume24h: 0.20
- spreadBps: 0.10
- trendStrength: 0.20
- volatility: 0.10
- volumeChange: 0.15
- signalQuality: 0.15
- dataReliability: 0.10

데이터 품질이 OK가 아닌 종목은 점수 보정으로 살리는 것이 아니라 후보에서 제외한다.

동점은 심볼 사전순으로 정렬한다.

기본 Top N은 10으로 제안되었으며 실제 운영 설정은 후속 구현에서 확정해야 한다.

### 7.6 멀티타임프레임 설계

조사 단계에서 검토한 시간 단위:
- 4H: 시장 방향
- 1H: 중기 추세
- 15m: 신호 탐색
- 5m: 선택적 확인
- 1m / 3m: 추가 검토 대상

최종 사용 시간 단위와 API 호출량은 아직 확정하지 않았다.

특히 시간 단위 수에 따라 API 호출량과 처리 시간이 달라지므로 구현 전에 다시 계산해야 한다.

상위 시간 단위의 완성 캔들이 하위 시간 단위 신호 시점에 실제로 확정되었는지 검증해야 한다. 단순 배열 인덱스 일치만으로 시간 정렬을 보장하지 않는다.

### 7.7 현재 구현 상태

`lib/multi-symbol-monitor.mjs`는 아직 생성되지 않았다.

따라서 다음 기능은 구현 완료로 간주하지 않는다.

## §11. 시장 데이터 및 시간 정렬 규칙

### 11.1 데이터 공급 원칙

- 1차 시장 데이터 공급원은 Bitget 공개 USDT-FUTURES API다.
- 계약 목록, 티커, 캔들은 각각 별도 데이터로 취급한다.
- API 응답이 정상이어도 데이터의 완전성은 별도로 검증한다.
- API 실패와 빈 응답을 정상적인 시장 데이터로 간주하지 않는다.
- 거래소 응답 원본과 정규화된 내부 데이터 구조를 구분한다.

### 11.2 캔들 데이터 규칙

기존 `bitget-candles.mjs`의 데이터 형식:

`{time, open, high, low, close, volume}`

- time은 밀리초 타임스탬프
- 가격과 거래량은 숫자
- 시간순 오름차순
- 중복 시간 제거 및 검증
- OHLC 관계 검증
- 유효하지 않은 가격과 데이터 거부
- 미완성 캔들은 확정 캔들로 사용하지 않는다.

### 11.3 시간 단위 정렬

멀티타임프레임 전략은 각 시간 단위의 캔들 종료 시점을 기준으로 정렬한다.

예를 들어 15분봉에서 신호를 계산할 때, 해당 신호 시점에 1시간봉과 4시간봉이 실제로 완료되었는지 확인해야 한다.

- 미래 캔들 참조 금지
- 상위 시간봉 미완성 데이터 사용 금지
- 캔들 시간대 혼합 금지
- 누락된 구간을 임의로 정상 데이터로 채우지 않는다.
- 거래소 시간과 서버 시간 차이를 점검한다.

### 11.4 데이터 품질 상태

권장 상태:
- OK
- INSUFFICIENT
- MISSING
- INVALID
- STALE
- FAILED

상태가 OK가 아닌 데이터는 전략 후보 선정에서 제외하거나 명시적으로 격리한다.

### 11.5 API 호출 및 부하 관리

- 거래소별 공식 API 제한을 우선 확인한다.
- 전체 종목 조회와 개별 종목 캔들 조회를 분리한다.
- 동시 요청 수와 재시도 횟수에 상한을 둔다.
- 429 및 서버 오류에는 Retry-After와 백오프 정책을 적용한다.
- 재시도가 무한 반복되지 않도록 한다.
- 캐시를 사용하더라도 데이터 최신 시각을 기록한다.
- 실제 호출량은 종목 수 × 시간 단위 수 × 페이지 수를 기준으로 계산한다.

## §12. 전략 및 포트폴리오 위험 관리 목표

### 12.1 전략 독립성

각 전략은 별도 식별자와 버전을 가져야 한다.

- 전략 이름
- 전략 버전
- 적용 시장
- 적용 방향
- 적용 시간 단위
- 진입 조건
- 청산 조건
- 손절 조건
- 포지션 크기
- 수수료 및 슬리피지 가정
- 검증 데이터 범위

전략 이름이 같더라도 파라미터가 다르면 별도 버전으로 관리한다.

### 12.2 Long / Short 분리

- Long과 Short 성과를 별도로 집계한다.
- 방향별 승률, 손익비, Profit Factor를 따로 기록한다.
- 한 방향의 수익으로 반대 방향의 손실을 숨기지 않는다.
- 시장 국면별 성과도 분리한다.
- Long 전용 전략을 검증 없이 Short로 뒤집어 사용하지 않는다.

### 12.3 종목별 위험

향후 통합 엔진에서 관리해야 할 항목:

- 종목별 최대 노출
- 종목별 허용 손실
- 종목별 증거금 사용량
- 레버리지
- 계약 수량 단위
- 최소 주문 수량
- 최소 주문 금액
- 거래소별 유지증거금 구간
- 펀딩 비용

### 12.4 포트폴리오 전체 위험

종목별 전략이 각각 통과하더라도 전체 포트폴리오가 안전하다는 뜻은 아니다.

다음을 별도 검증한다.

- 총 사용 증거금
- 전체 Long 노출
- 전체 Short 노출
- 순방향 노출
- 종목 간 상관관계
- 동일 섹터 및 유사 자산 집중도
- 동시 포지션 수
- 일일 손실 한도
- 최대 낙폭
- 급격한 변동성 확대 시 동시 손실 위험

### 12.5 Grid 전략의 추가 위험

Adaptive Grid는 일반적인 단일 진입 전략과 다른 위험이 있다.

- 추세가 지속될 때 포지션이 한쪽으로 누적될 수 있다.
- 급격한 가격 이동에서 주문 간격이 적절하지 않을 수 있다.
- 수수료와 펀딩이 반복적으로 누적된다.
- 그리드 추가 진입으로 증거금이 빠르게 증가할 수 있다.
- 손절 없는 무한 물타기를 허용해서는 안 된다.
- 변동성 및 시장 국면에 따라 그리드를 중단하는 조건이 필요하다.

### 12.6 성과 지표

최소한 다음을 전략별·종목별·방향별·포트폴리오별로 기록한다.

- Net PnL
- Gross PnL
- 수수료
- 펀딩 비용
- 승률
- 평균 수익
- 평균 손실
- Profit Factor
- 최대 낙폭(MDD)
- 거래 횟수
- 평균 보유 시간
- 연속 손실
- 자본 사용률
- 청산 및 강제 종료 관련 위험

수익률만으로 전략을 승인하지 않는다.

## §13. 백테스트 및 Paper Forward 승인 기준

### 13.1 백테스트 기본 조건

- 데이터 출처와 기간을 기록한다.
- 캔들 개수와 누락 구간을 기록한다.
- 수수료와 슬리피지 가정을 명시한다.
- 펀딩 데이터가 없으면 미반영 사실을 명시한다.
- 미래 데이터 참조 여부를 테스트한다.
- IS/OOS 데이터 분리를 적용한다.
- 동일 데이터로 반복 튜닝한 결과를 독립 검증 성과로 주장하지 않는다.

### 13.2 결과의 신뢰성

백테스트 결과에는 다음 정보가 필요하다.

- 전략 ID 및 버전
- 거래소와 시장
- 심볼
- 시간 단위
- 데이터 시작 및 종료 시각
- 초기 자본
- 최종 자본
- 수수료와 슬리피지
- 총 거래 수
- 방향별 거래 수
- 순손익
- Profit Factor
- MDD
- 실패 원인
- 테스트 완료 상태

결과가 없거나 필수 값이 누락되면 PASS로 처리하지 않는다.

### 13.3 Failure Memory

Failure Memory는 전략 실패와 재발 방지에 활용한다.

기록 대상:
- 전략 식별자와 버전
- 테스트 조건
- 실패 유형
- 실패 근거
- 손실 및 위험 지표
- 데이터 품질 문제
- 재검증 조건
- 해결 여부

기존 Failure Memory는 사용자 승인 없이 수정·삭제하지 않는다.

### 13.4 Paper Forward

Paper Forward는 과거 데이터 백테스트와 분리된 별도 검증 단계다.

검증 대상:
- 실시간 공개 시장 데이터 수신
- 신호 발생 시각
- 가상 진입 및 청산
- 가상 체결 가격
- 수수료
- 펀딩
- 포지션 및 잔고
- 재시작 후 상태 복구
- 중복 이벤트 방지
- 장시간 운영 안정성

Paper Forward가 실행되었다는 사실만으로 수익성이 입증된 것은 아니다.

### 13.5 승인 단계 구분

- PASS: 해당 단계의 명시된 테스트 조건 통과
- FAIL: 필수 조건 미충족
- BLOCKED: 외부 데이터나 필수 의존성 부족
- NOT_RUN: 아직 실행하지 않음
- NOT_COMPUTED: 계산 모델 미구현

PASS는 해당 검증 범위에만 적용한다. 한 BLOCK의 PASS를 전체 시스템 완성으로 확대 해석하지 않는다.
